## 解析与依赖核对

依赖为 `vendor/OpenWar3AI-ffd7dd25a3c2478f457b74bde89d23e605b24243`。

`sdk/python/w3world.py:parse_units` 从 detail 头读取 `na`，连续解包 `min(na,12)` 条技能；没有根据被动技能、光环 code 或 flags 提前退出的分支。SDK `Game.abilities` 只是转换这些记录。本项目没有过滤掉光环后的英雄技能。这把调查范围缩到运行时发布数据/协议，而不是当前保蓝或物品识别策略。

**缺少原始共享内存字节与原生源码，不能断言已经定位到某一条 C++ 链表语句，也不能完全排除协议布局问题。** 上游应对比拾取前后同一 DK 的 detail index、`na`、12 个原始槽位及原生完整技能链表，检查遍历遇到物品光环节点时的 next 指针、类型判断与提前返回，再核验 `AUdc` 等级和实际冷却。

本机 `render_hook.dll` 版本 `2026.09.26.1644`，SHA-256：
`92bb7e6b75e56f91e7eb905844b9a28085e88d4d991a547522c7da8c2907da97`。
2026-10-20 读取的[官方 main 发布清单](https://github.com/OPENXXAI/OpenWar3AI/blob/main/prebuilt/manifest.json)仍是相同版本和哈希。公开仓库未提供该 native 源码，未发现可替换的新 DLL；没有擅自更新运行依赖。读取副本保存在 `artifacts/upstream-manifest.json`。

JASS 文档虽有 `GetUnitAbilityLevel`，但本依赖没有独立的完整冷却查询接口，且通用调用涉及开发权限；仅补技能等级不能证明已修复冷却和完整枚举。本轮未绕过公平接口使用开发调用。
